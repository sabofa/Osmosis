# Tutor Phases 2, 4, 5, 7 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the four remaining phases of the tutor item-engine integration that don't need real production data or an unverified dependency to build safely: ingestion metadata (Phase 2), node-grain identity (Phase 7 — small enough to fold into Phase 2's migration), rich diagnostic outcomes (Phase 4), and interval-based retention scheduling (Phase 5). Phase 6 (retrospective audit) and Phase 8 (session sandbox extras) are explicitly excluded from this plan — see "Scope" below.

**Architecture:** All four phases are additive schema + domain-layer + MCP-layer work on the existing `question`/`choice`/`response`/`attempt` tables and the existing `create_questions`/`answerResponse`/`present_item` code paths (all already shipped and reviewed in the prior Phase 1 plan). Phase 5 adds one genuinely new table (`retention_schedule`) and two new MCP tools. Nothing in this plan touches the app's rendering surfaces except Task 3's `Take.tsx` confidence/IDK control, which is additive UI on an existing, already-working answer flow.

**Tech stack:** TypeScript, `node:sqlite` `DatabaseSync`, Zod (`server/src/mcp/tools.ts`), Vitest (`server/tests/`), React (`web/src/`).

**Spec:** `docs/superpowers/plans/2026-09-01-tutor-item-engine-integration.md`, Phases 2, 4, 5, 7 (Phase 1 of that same document, already shipped, is this plan's prerequisite — `presentItem`, `quickCheck`, `answerResponse`, `createAttempt` etc. all already exist).

## Scope

**In scope:** Phase 2 (ingestion metadata) + Phase 7 (node_key identity) combined into one migration and one task, since both are additive nullable columns on `question`. Phase 4 (rich outcomes). Phase 5 (scheduling).

**Explicitly out of scope, per the source plan's own text — do not implement:**
- **Phase 6** (retrospective audit) — the source plan says "this phase should not be started until Phase 4 has shipped and accumulated real response history." Building discrimination statistics against an empty or synthetic-seed database risks tuning thresholds to be meaningless in production.
- **Phase 8** (session sandbox extras: interactive checkpoints, attempt capture, scaffold dial, etc.) — has an unverified dependency (whether `graph-engine`'s renderer supports learner-editable input at all) and its own unresolved Decision Points around a new `session_checkpoint` schema. Not safe to build on a guess.

## Global Constraints

- **Decision Point rulings** (each carried from the source plan's own recommended default — restated here as binding for this plan, not re-litigated per task):
  - `tests_error` (Task 1) and `misapplied_method` (Task 2) are free text, not an enum — the source plan explicitly recommends this until real usage shows the actual taxonomy, matching how `tag` itself started free-form.
  - `claim_rung` lands as a bare nullable column on `question` (Task 1), not a `question_node` join table — the source plan recommends this now and revisiting only once Phase 7's `node_key` actually needs multi-node support for one question, which isn't yet a real requirement.
  - `misconception` is required at the application layer (in `createQuestions`'s validation) on every non-correct MC choice going forward, even though the DB column stays nullable for backward compatibility with pre-existing rows (Task 2). This matches the source plan's framing that distractor rationale is the point of items in this system, not an optional enrichment.
  - Confidence is a 3-point scale (`unsure`/`somewhat`/`confident`), not a continuous slider (Task 2) — cheap to answer under time pressure, per the source plan's own citation.
  - `idk` is a separate boolean, not a 4th confidence value (Task 2) — "I don't know" must stay a distinct third outcome, not a point on the confidence scale.
  - `retention_schedule.identity_key` accepts either a tag slug or a `node_key` string in the same column — disambiguated by which the caller supplies, not by a type discriminator column (Task 4) — matching Phase 7's own recommendation that node keys and tag slugs occupy the same identity "slot."
  - Multiple retention targets per identity: `UNIQUE(identity_key, retention_target)` allows several open rows per identity; `next_due_for_identity` takes the *minimum* `due_at` across all of an identity's rows (Task 4).
- **Migrations are additive, forward-only SQL files** under `server/migrations/`, numbered sequentially after the current highest existing file. **Confirm the real highest number immediately before Task 1** — this plan assumes `010_tutor_sessions.sql` is current highest (verified 2026-09-02), so this plan's migrations are `011` and `012`; re-verify if time has passed.
- **Every new/changed domain function gets a Vitest test** using `openTestDb()`/`insertTag()`/`insertQuestion()` from `server/tests/helpers.ts`.
- **Zod schemas in `mcp/tools.ts` must mirror DB `CHECK` constraints exactly** (same enum values) so a schema violation is caught by Zod with a legible error before it ever reaches SQLite.
- Run `cd server && npm run typecheck && npm test` before every commit — no known pre-existing typecheck issues on this branch, a genuinely clean `tsc` run is the bar.

-- server/migrations/013_retention_schedule.sql
CREATE TABLE retention_schedule (
    id               TEXT PRIMARY KEY,
    identity_key     TEXT NOT NULL,
    retention_target TEXT NOT NULL,
    first_gap_days   REAL NOT NULL,
    due_at           TEXT NOT NULL,
    last_result      TEXT NOT NULL DEFAULT 'never_attempted'
                       CHECK (last_result IN ('pass', 'fail', 'never_attempted')),
    target_source    TEXT NOT NULL CHECK (target_source IN ('engine', 'tutor_direct')),
    created_at       TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at       TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE (identity_key, retention_target)
);
CREATE INDEX retention_schedule_due ON retention_schedule (due_at);
CREATE INDEX retention_schedule_identity ON retention_schedule (identity_key);
```

Note: no `CHECK (first_gap_days >= 1)` — sub-1-day gaps for sub-floor probes must remain legal, per the source plan's explicit warning.

// server/src/domain/retention.ts
import type { DatabaseSync } from "node:sqlite";
import { v4 as uuidv4 } from "uuid";
import { DomainError } from "./errors.js";

export interface SetRetentionTargetInput {
  identity_key: string;
  retention_target: string;
  target_source: "engine" | "tutor_direct";
  needs_last_until: string; // ISO date or datetime the material needs to last until
}

// Cepeda et al. 2008: optimal first gap is ~20-40% of the retention interval,
// dropping to 5-10% for year-long targets. Linear interpolation between the
// two known bands, clamped at the boundaries — not a precise model, a
// reasonable default per the source plan's own framing.
function firstGapRatio(totalDays: number): number {
  if (totalDays <= 14) return 0.3; // midpoint of 20-40%
  if (totalDays >= 365) return 0.075; // midpoint of 5-10%
  // Linear interpolation between (14, 0.3) and (365, 0.075).
  const t = (totalDays - 14) / (365 - 14);
  return 0.3 + t * (0.075 - 0.3);
}

export function setRetentionTarget(
  db: DatabaseSync,
  input: SetRetentionTargetInput
): { id: string; due_at: string; first_gap_days: number } {
  const now = Date.now();
  const target = new Date(input.needs_last_until).getTime();
  const totalDays = Math.max((target - now) / (1000 * 60 * 60 * 24), 0);
  const firstGapDays = totalDays * firstGapRatio(totalDays);
  const dueAtMs = now + firstGapDays * 24 * 60 * 60 * 1000;
  const dueAt = new Date(dueAtMs).toISOString().replace("T", " ").slice(0, 19);

  const id = uuidv4();
  db.prepare(
    `INSERT INTO retention_schedule (id, identity_key, retention_target, first_gap_days, due_at, target_source)
     VALUES (?, ?, ?, ?, ?, ?)
     ON CONFLICT (identity_key, retention_target) DO UPDATE SET
       first_gap_days = excluded.first_gap_days,
       due_at = excluded.due_at,
       target_source = excluded.target_source,
       updated_at = datetime('now')`
  ).run(id, input.identity_key, input.retention_target, firstGapDays, dueAt, input.target_source);

  const row = db
    .prepare("SELECT id, due_at, first_gap_days FROM retention_schedule WHERE identity_key = ? AND retention_target = ?")
    .get(input.identity_key, input.retention_target) as { id: string; due_at: string; first_gap_days: number };
  return row;
}

export function getNextDueForIdentity(db: DatabaseSync, identityKey: string): string | null {
  const row = db
    .prepare(
      `SELECT MIN(due_at) AS due_at FROM retention_schedule
       WHERE identity_key = ? AND last_result != 'fail'`
    )
    .get(identityKey) as { due_at: string | null };
  return row.due_at;
}

export function getDueItems(
  db: DatabaseSync,
  opts: { before?: string; limit?: number; offset?: number } = {}
): { total: number; items: unknown[]; has_more: boolean } {
  const before = opts.before ?? new Date().toISOString().replace("T", " ").slice(0, 19);
  const limit = opts.limit ?? 50;
  const offset = opts.offset ?? 0;

  const total = (
    db.prepare("SELECT COUNT(*) AS n FROM retention_schedule WHERE due_at <= ?").get(before) as { n: number }
  ).n;

  const items = db
    .prepare(
      `SELECT id, identity_key, retention_target, due_at, last_result, target_source
       FROM retention_schedule WHERE due_at <= ? ORDER BY due_at ASC, id ASC LIMIT ? OFFSET ?`
    )
    .all(before, limit, offset);

  return { total, items, has_more: offset + items.length < total };
}

export function recordRetentionResult(db: DatabaseSync, identityKey: string, retentionTarget: string, passed: boolean): void {
  const row = db
    .prepare("SELECT id FROM retention_schedule WHERE identity_key = ? AND retention_target = ?")
    .get(identityKey, retentionTarget) as { id: string } | undefined;
  if (!row) throw new DomainError("not_found", `No retention_schedule row for "${identityKey}"/"${retentionTarget}".`);
  db.prepare("UPDATE retention_schedule SET last_result = ?, updated_at = datetime('now') WHERE id = ?").run(
    passed ? "pass" : "fail",
    row.id
  );
}
```

**Note on `firstGapRatio`:** this is a genuinely new piece of logic the source plan didn't fully specify (it gave a 4-row table, not a formula) — the linear interpolation above is a reasonable, simple way to turn that table into a continuous function, but it's an implementation judgment call, not something copied from the plan verbatim. If the tutor later wants the exact 4-band table behavior (hours/3-6 days/2.5-5 weeks/months as discrete buckets rather than smoothly interpolated), this function is the one place to change.

import { setRetentionTarget, getDueItems } from "../domain/retention.js";

server.registerTool(
  "set_retention_target",
  {
    description:
      "Tell Osmosis how long a piece of content needs to be retained, and let Osmosis compute when to resurface it. You supply the target and reason; Osmosis owns scheduling — never call this expecting to control exact timing.",
    inputSchema: {
      identity_key: z.string().describe("A tag slug or node_key — whatever identity this retention target applies to."),
      retention_target: z.string().describe("A label for this specific target, e.g. 'chapter-8-test' or 'final-exam'. One identity can have several open targets."),
      target_source: z.enum(["engine", "tutor_direct"]).describe("'engine' if this came from a published assessment date; 'tutor_direct' if you set it yourself for a self-directed topic."),
      needs_last_until: z.string().describe("ISO date/datetime the material needs to be retained until."),
    },
  },
  async ({ identity_key, retention_target, target_source, needs_last_until }) => {
    try {
      return ok(setRetentionTarget(db, { identity_key, retention_target, target_source, needs_last_until }));
    } catch (err) {
      return fail(err);
    }
  }
);

server.registerTool(
  "get_due_items",
  {
    description: "List identities whose retention schedule is due now (or before a given time), most-overdue first. Paginated.",
    inputSchema: {
      before: z.string().optional(),
      limit: z.number().optional(),
      offset: z.number().optional(),
    },
  },
  async ({ before, limit, offset }) => {
    try {
      return ok(getDueItems(db, { before, limit, offset }));
    } catch (err) {
      return fail(err);
    }
  }
);
